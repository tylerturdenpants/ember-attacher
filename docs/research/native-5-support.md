## Executive Verdict

Whereas [#1058](https://github.com/tylerturdenpants/ember-attacher/blob/research/native-fallback/docs/research/native-fallback.md) established that **4.x** must retain `@floating-ui/dom` behind feature detection to preserve the 3.x/4.x component contract, **late-2026 browser support makes a native-first 5.x architecture viable across all three engine families (Blink, Gecko, WebKit)**—with four specific boundary conditions where native web platform primitives either remain single-engine or differ structurally from `@floating-ui/dom`:

1. **Works 100% natively across Baseline browsers today (Chrome/Edge, Firefox, Safari macOS/iOS):**
   - **Top-layer host & lifecycle:** `popover="auto" | "manual"`, `:popover-open`, `showPopover()` / `hidePopover()` / `togglePopover()`, `beforetoggle` / `toggle` events, `popovertarget`, `commandfor` / `command`, and `showPopover({ source })` (both focus order and implicit CSS anchor reference).
   - **Core CSS Anchor Positioning (Level 1):** `anchor-name`, `anchor-scope`, `position-anchor`, `position-area` (3×3 grid), `@position-try`, `position-try-fallbacks` (`flip-block`, `flip-inline`, `flip-start`, `flip-x`, `flip-y`, `<position-area>`), `anchor()`, `anchor-size()`, `anchor-center` (automatic cross-axis safety shift within the containing block), and `position-visibility: no-overflow`.
   - **Nested attachments:** Native `popover="auto"` (and `"hint"` where supported) preserves nested attachment hierarchies via the HTML spec's *topmost popover ancestor* algorithm—even when the child attachment's **Host** is portaled outside the parent attachment in the DOM—provided the **Trigger** lies inside the parent attachment and passes `source` (or uses `popovertarget` / `commandfor`).
   - **Non-modal top-layer dialog:** `<dialog popover="auto" | "manual">` places a semantic `<dialog>` **Host** in the browser top layer without making the document `inert` (unlike `showModal()`) and without losing top-layer promotion (unlike `dialog.show()`).

2. **Still requires JS or a fallback / cannot be done 100% declaratively across all engines in late 2026:**
   - **Flip-aware tethered arrows (`@arrow: true` + `@flip`):** Moving an arrow along the **Target** edge works across all engines via `position-area` / `anchor-center`, but **flipping the arrow's side and rotation when `position-try-fallbacks` activates** requires **CSS Anchor Positioning Level 2 Anchored Container Queries** (`container-type: anchored` + `@container anchored(fallback: ...)`), which is **Chromium-only (Chrome/Edge 143+)** and unsupported in Firefox and Safari.
   - **Declarative hover/focus triggers (`interestfor`) & `popover="hint"`:** `interestfor` is still an **experimental Chromium-only proposal** (`chrome: 142` behind flag / `149` origin/release, `standard_track: false`, unsupported in Firefox and Safari). `popover="hint"` reached stable in Chrome/Edge 151 (Jul 2026), Firefox 153 (Jul 2026), and Safari 27.3 (late 2026), so 5.x still needs thin JS `mouseenter`/`mouseleave`/`focus`/`blur` listeners (or `popover="manual"` for tooltips if supporting Safari < 27.3).
   - **Virtual targets (`{ getBoundingClientRect() }`):** CSS Anchor Positioning can only tether to a real DOM `Element` in the layout tree (`anchor-name` or implicit `source`). Virtual targets require either `@floating-ui/dom` or a 0×0 `position: fixed` proxy `Element` synced to the virtual rect.
   - **Custom `@overflowPadding` and `limitShift()` clamping, `@isOffset` cursor polygon, and cross-browser top-layer exit animations:** CSS `anchor-center` shifts to the containing-block edge (`0px` padding, extendable via `margin` on the attachment) without Floating UI's `limitShift()` target-edge stop; exit transitions from the top layer cannot rely on CSS `overlay` + discrete `display` in Firefox (bug 1882408) or Safari (`overlay` unsupported) and need a `getAnimations()` / `transitionend` delay before calling `hidePopover()`.

## 3. Deep Dive: How Native Primitives Map to `ember-attacher` 5.x

### 3.1 Placement & Flip Mapping (`@placement` + `@flip`)

In `ember-attacher` 4.x, `@placement` accepts Floating UI's 12 placements (`top`, `top-start`, `top-end`, `bottom`, `bottom-start`, `bottom-end`, `left`, `left-start`, `left-end`, `right`, `right-start`, `right-end`). In CSS Anchor Positioning Level 1, each maps directly to `position-area`:

| `ember-attacher` `@placement` | CSS `position-area` (Physical) | Default `position-try-fallbacks` (when `@flip` unset & `@overflowPadding !== false`) |
| --- | --- | --- |
| `top` | `top` *(computes to `top span-all`)* | `flip-block` |
| `top-start` | `top span-right` | `flip-block, top span-left, flip-block flip-inline` |
| `top-end` | `top span-left` | `flip-block, top span-right, flip-block flip-inline` |
| `bottom` | `bottom` *(computes to `bottom span-all`)* | `flip-block` |
| `bottom-start` | `bottom span-right` | `flip-block, bottom span-left, flip-block flip-inline` |
| `bottom-end` | `bottom span-left` | `flip-block, bottom span-right, flip-block flip-inline` |
| `left` | `left` *(computes to `left span-all`)* | `flip-inline` |
| `left-start` | `left span-bottom` | `flip-inline, left span-top, flip-block flip-inline` |
| `left-end` | `left span-top` | `flip-inline, left span-bottom, flip-block flip-inline` |
| `right` | `right` *(computes to `right span-all`)* | `flip-inline` |
| `right-start` | `right span-bottom` | `flip-inline, right span-top, flip-block flip-inline` |
| `right-end` | `right span-top` | `flip-inline, right span-bottom, flip-block flip-inline` |

When the caller passes an explicit space-delimited `@flip="bottom left right"`, each token maps via the same table into a comma-separated `position-try-fallbacks` list (e.g. `position-try-fallbacks: bottom, left, right`).

**Critical UA Reset on `[popover]`:**
Browsers apply `position: fixed; inset: 0; margin: auto;` in the UA stylesheet for `[popover]` elements to center them in the viewport. When tethering an **Attachment** via `position-area`, `ember-attacher.css` **must** reset `inset: auto; margin: 0;` (gated inside `@supports (position-area: top)` if supporting pre-anchor browsers, or unconditional in 5.x where anchor positioning is required).

### 3.2 Implicit vs Named Anchor Linking (`showPopover({ source })` vs `anchor-name`)

There are two ways to link an **Attachment** to its **Target** in 5.x:

1. **Programmatic `showPopover({ source: targetElement })` (Implicit Anchor):**
   - Supported across Chrome/Edge 137+, Firefox 147+, Safari 26+ (`Baseline Low` since 2026-01-13).
   - Automatically sets the **Target** as the **Attachment**'s implicit anchor (`position-anchor: auto`), places the **Attachment** next in keyboard focus order, and registers the **Target**'s containing popover as the parent in the *topmost popover ancestor* algorithm.
   - **Caveat:** WHATWG HTML (`#check-popover-validity` / `#show-popover`) and CSS Anchor Positioning require `source` to be an `Element`. Furthermore, in some early implementations `source` focus management expected focusable elements, whereas `ember-attacher` targets can be arbitrary elements (`<span>`, `<div>`, `<svg>`).

2. **Explicit `anchor-name: --ea-${id}` on Target + `position-anchor: --ea-${id}` on Attachment:**
   - Supported across Chrome/Edge 125+, Firefox 147+, Safari 26+ (`Baseline Low` since 2026-01-13).
   - Works on **any** `Element` (HTML or SVG) regardless of how the popover is opened (`popover="manual"`, `popover="auto"`, or non-popover), and across `{{#in-element}}` portals because `anchor-name` lookup is tree-scoped, not ancestor-scoped.

**Best practice for 5.x:** Always set `anchor-name: --ea-${id}` on the **Target** and `position-anchor: --ea-${id}` on the **Attachment** for rock-solid positioning, **and** pass `{ source: target }` to `showPopover({ source: target })` whenever `target instanceof HTMLElement` to get native focus order and nested popover ancestry.

### 3.3 The Arrow Problem (`@arrow: true`) and Ways to Solve It in 5.x

In 4.x (`ember-attacher.css#L25-L85`), `.ember-attacher-arrow` is a `10px × 10px` square rotated 45° with two colored borders, positioned via `[x-placement^=top|bottom|left|right]` and offset along the cross-axis via `middlewareData.arrow.{x,y}`.

In pure CSS Anchor Positioning:
- **Cross-axis tethering works in Level 1 (Baseline Low):** Because the arrow is an absolutely positioned child inside the **Attachment**, if the **Attachment** does not establish a new anchor scope or if the arrow inherits `position-anchor: inherit`, the arrow can align itself to the **Target**'s center (`justify-self: anchor-center` / `align-self: anchor-center` or `left: anchor(center)` / `top: anchor(center)`), staying centered on the **Target** even when the **Attachment** shifts near the viewport edge.
- **Main-axis flipping requires Level 2 (`@container anchored(fallback: ...)`):** When `position-try-fallbacks: flip-block` flips a `top` attachment to `bottom`, the arrow must move from `bottom: -5px; transform: rotate(-45deg)` to `top: -5px; transform: rotate(135deg)`. In pure CSS, only `@container anchored(fallback: flip-block)` can detect that fallback state—and as of late 2026, `@container anchored(...)` is **only supported in Chrome/Edge 143+** (not Firefox 147+, not Safari 26/27).

**How 5.x can handle `@arrow: true` without `@floating-ui/dom`:**
Instead of keeping `@floating-ui/dom` solely for arrows in Firefox and Safari, 5.x can use a **10-line JS side-observer** after `showPopover()` (and on scroll/resize when `@arrow` or directional animations are active): compare `target.getBoundingClientRect()` and `floatingElement.getBoundingClientRect()` (e.g. `floatingRect.bottom <= targetRect.top` → `'top'`, `floatingRect.top >= targetRect.bottom` → `'bottom'`, etc.) and write `x-placement` (or `data-placement`). That preserves 100% of `ember-attacher.css`'s existing `[x-placement^=...]` arrow and directional animation rules across Chrome, Firefox, and Safari while letting CSS Anchor Positioning do all layout, flipping, and shifting natively!

### 3.4 Virtual Targets (`getBoundingClientRect`) Without `@floating-ui/dom`

`ember-attacher` supports virtual targets (`{ getBoundingClientRect(), contextElement? }`) via `target-resolution.js`. CSS Anchor Positioning cannot reference a plain JS object. In 5.x without `@floating-ui/dom`, `BasicAttacher` can support virtual targets with a tiny **proxy anchor element**:
1. When `isVirtualReference(target)` is true, create (or render) a `<div class="ember-attacher-virtual-anchor" aria-hidden="true">` with `position: fixed; pointer-events: none; visibility: hidden; margin: 0; padding: 0; anchor-name: --ea-${id};`.
2. Sync its `top`, `left`, `width`, and `height` from `target.getBoundingClientRect()` on show (and in a `requestAnimationFrame` / scroll listener when `autoUpdate` is enabled).
3. CSS Anchor Positioning on the **Attachment** then positions, flips, and shifts against `--ea-${id}` identically to a real DOM **Target**.
