# Keep @floating-ui/dom for Positioning with In-Place Top-Layer popover="manual" Host and WAAPI Exit Lifecycle

Starting in 4.3 and completed in 5.0, `ember-attacher` keeps `@floating-ui/dom` (`computePosition`, `autoUpdate`, `@middleware`) as its single positioning engine while rendering `<div class="ember-attacher" popover="manual">` directly in place in a single render pass (`showPopover()` / `hidePopover()`) as the Top-Layer **Host**. `{{#in-element}}`, `<meta hidden>`, and `@floatingElementContainer` portaling are removed in 5.0 for components; only the imperative singleton `{{tooltip}}` pool (`TooltipDomHost`) mounts its shared node in `modalContainer || ownerRootElement || document.body`.

Show/hide animations use CSS `@starting-style`, `transition-property: transform, opacity, display, overlay;`, and `transition-behavior: allow-discrete;` with `:is(:popover-open, .\:popover-open, [data-open]):where(:not([data-closing]))` and `[data-closing]` (`pointer-events: none`), awaiting `floatingElement.getAnimations({ subtree: true })` (with a `hideDuration` timer fallback) instead of `@ember/runloop` timers. Spatial motion is gated inside `@media (prefers-reduced-motion: no-preference)`, reduced-motion fades are capped at `100ms`, and idle overlays avoid permanent `will-change` or `perspective` layers. Without native Popover API support, hosts degrade to `[data-open]` / `[data-closing]` in place.

We rejected switching positioning to CSS Anchor Positioning (or maintaining a dual CSS Anchor + Floating UI positioning engine) and rejected switching the **Host** tag to `<dialog>`. CSS Anchor Positioning cannot execute JavaScript `@middleware` functions (`flip`, `shift`, `offset`, `size`, `inline`, `hide`, custom `{ name, fn }`) and requires extra shims for flip-aware arrows and `VirtualElement` targets, whereas `<div class="ember-attacher" popover="manual">` escapes clipping and `z-index` contexts cleanly with full `@middleware` and `VirtualElement` parity.
